# 前端可执行实现方案

## 项目背景与目标

本文档基于当前项目源码与《前端对接接口分析.md》整理，目标不是重新设计一套全新的后台系统，而是在现有 `Vue3 + JavaScript + Electron` 单页桌宠应用基础上，给出一份可直接落地的前端实现方案。

本方案覆盖三类内容：

1. 对现有已上线能力做接口对齐和风险修正，包括登录、聊天、审批、历史、状态流、计划、查询中心。
2. 在保持当前界面风格与交互模式的前提下，扩展可管理、可调试的新模块，包括 MCP 能力中心、Prompt 治理中心、Prompt 策略管理、RAG 调试面板。
3. 明确开发分层、页面结构、组件拆分、接口触发时机、字段使用方式、状态流转、异常边界与开发顺序，保证后续前端可以按文档直接实施。

执行原则：

- 严格复用当前项目的浮层面板式交互，不改成传统后台页面。
- 严格通过现有 Electron 请求链路接入，不新增第二套直连请求方案。
- 严格按接口文档字段使用，不擅自重命名、推测或裁剪后端字段。
- 严格标识当前源码中的旧接口、兼容接口、退役接口，避免继续扩散错误对接方式。

## 当前项目现状分析

### 1. 技术栈与运行方式

- 前端框架为 `Vue 3 + JavaScript`。
- 宿主环境为 `Electron`，主窗口为透明全屏桌宠窗口。
- 路由非常轻量，当前只有 `/index` 一个主页面，所有业务都挂在 `src/views/index/index.vue`。
- 当前没有使用 Pinia/Vuex，状态以页面内 `ref/reactive` 与 `composables` 为主。
- 真实请求链路为：
  `Renderer(src/api/index.js) -> preload(electron/preload.js) -> ipcMain(electron/main.js / src/main/ipc/*.js) -> axios(src/main/httpClient.js) -> http://localhost:8001`
- `src/utils/request.js` 是旧的 Web 侧 axios 封装，依赖 `/api` 前缀和前端路由跳转，当前 Electron 主链路并不使用，后续不应继续扩展。

### 2. 当前页面结构

当前主页面 `src/views/index/index.vue` 已经承担了完整的壳层职责，核心 UI 由以下组件组成：

- `ChatInput.vue`
  底部聊天输入条，负责打开设置、历史、查询、计划。
- `HistoryPanel.vue`
  历史聊天回放面板。
- `QueryPanel.vue`
  当前的数据查询面板，已有筛选表单、表格、分页、拖拽、缩放能力。
- `PlanPanel.vue`
  计划执行中心，已经具备计划执行、图谱快照展示、异步事件展示能力。
- `SettingsPanel.vue`
  设置面板，已有主题、外貌、系统状态与 Tool/Skill 管理入口。
- `ApprovalModal.vue`
  审批弹窗，已有倒计时、参数 JSON 展示、拖拽能力。

可以确认当前项目最强的复用资产不是“业务表单”，而是“浮层面板壳 + 表格/卡片/弹窗交互模式 + 主题变量体系 + SSE 驱动式状态更新”。

### 3. 当前界面风格与美化规范

现有项目的视觉基调非常明确，后续新页面必须保持一致：

- 深色赛博/终端风格，主色以 `--primary` 为核心，默认是青绿色霓虹。
- 面板大量使用半透明渐变背景、描边、模糊、内阴影和外发光。
- 页面不是“铺满白底后台”，而是“悬浮卡片 + 透明桌面 + 可拖拽组件”。
- 大部分业务窗口支持拖拽、缩放、全屏切换。
- 按钮层级清晰：
  主操作使用高亮主色按钮；
  次操作用描边或低对比度按钮；
  危险操作使用红色系。
- 反馈方式偏轻提示与局部面板反馈，已有 `appearance.showAppearanceHint` 和面板内 toast 两类机制。

后续新增页面不能切成传统管理后台风格，必须继续采用当前的浮层运维台风格。

### 4. 当前状态管理方式

当前项目的状态方式适合继续沿用：

- 页面级局部状态：`index.vue` 内部维护聊天、登录、审批、面板显隐、模型状态。
- 领域级状态：通过 `useTheme`、`useAppearance`、`useRhythm`、`usePlanGraphStore` 等 composable 管理。
- 持久化只用于 UI 偏好与模型参数：
  主题、特效、模型显隐、位置、追踪原点、外貌开关等都走 `localStorage` 或 `sessionStorage`。
- 鉴权 token 当前由 Electron 主进程 `src/main/httpClient.js` 内存持有，不走本地持久化。

结论：后续新增模块优先继续使用 composable/store 方式扩展，不建议在这一轮为了后台功能单独引入 Pinia。

### 5. 当前项目中必须修正的对接问题

| 问题点 | 当前位置 | 现状 | 后续要求 |
| --- | --- | --- | --- |
| 审批提交仍走旧兼容接口 | `src/main/ipc/mcpIpc.js`、`electron/preload.js`、`src/views/index/index.vue` | 当前 `approveSkill` 调的是 `/mcp/skills/approval` | 新实现统一切换到 `/mcp/tools/approval`，旧接口只保留兼容兜底说明 |
| Tool CRUD 仍走退役接口 | `src/main/ipc/mcpIpc.js`、`src/views/settings/ToolManager.vue` | `create/update/delete` 仍调用 `/mcp/tools` | 不再继续扩展旧 ToolManager 写路径，改为 MCP 能力中心 + migrate 系列接口 |
| Skill CRUD 仍走退役接口 | `src/main/ipc/mcpIpc.js`、`src/views/settings/SkillManager.vue` | `create/update/delete` 仍调用 `/mcp/skills` | 不再继续扩展旧 SkillManager 写路径，改为 MCP 能力中心/工作流目录/策略目录 |
| 查询中心仍暴露退役查询 | `electron/main.js`、`src/components/QueryPanel.vue` | `memory`、`user-preference` 两个 tab 调用退役接口 | 查询中心只保留知识库与日志，RAG 调试单独新增；退役 tab 不再继续调用 |
| `shutdown` 被当成聊天回复处理 | `src/views/index/index.vue` | `/luna/api/chat/shutdown` 成功无响应体，但当前 `callShutdown` 仍尝试走 `handleModelReply` | 关闭会话必须改成静默请求，成功只做资源回收，不刷新聊天内容 |
| `disconnect` 需要鉴权 | `src/main/ipc/chatIpc.js`、`electron/main.js` | 退出登录后清 token 再断流，存在断流请求 401 风险 | 断 SSE 必须在 token 清理前完成 |
| Legacy request 封装存在误导 | `src/utils/request.js` | 仍保留 Web 侧 `/api` 请求与 router 401 跳转逻辑 | 后续所有新接口只走 Electron 主链路，不再复用该文件 |

## 接口对接方案

### 1. 认证与会话方案

#### 1.1 登录

- 触发位置：
  登录浮层提交按钮。
- 前端校验：
  `username`、`password` 非空。
- 请求：
  `POST /auth/login`。
- 成功处理：
  保存 token 到主进程 `httpClient`；
  自动建立 SSE；
  关闭登录浮层；
  启动开场动画与 `startup`。
- 失败处理：
  在登录面板原位展示错误文本，不弹系统 alert。

#### 1.2 启动会话

- 触发位置：
  登录成功后的 boot 结束时。
- 请求：
  `POST /luna/api/chat/startup`。
- 展示方式：
  使用当前 `handleModelReply` 的打字/气泡输出链路。
- 注意事项：
  如果返回 `context_governance_blocked`，页面显示阻断原因，不要当成网络错误。

#### 1.3 退出登录与关闭会话

- `logout` 与 `shutdown` 的职责必须拆开：
  `shutdown` 用于当前会话收尾；
  `logout` 用于 token 吊销。
- 推荐顺序：
  先 `shutdown`；
  再 `disconnect`；
  最后 `logout` 和清理 token。
- `shutdown` 成功没有响应体，前端只做静默成功处理，不进入聊天回复渲染。

### 2. 聊天、状态流与审批方案

#### 2.1 SSE 统一入口

- 页面初始化后建立一次 `/api/luna/status/stream`。
- 所有运行时事件都走同一条流，不拆多条连接。
- 前端解析必须先按 `event` 名称分流，再处理 `data`，不能把所有 payload 当成统一结构。

建议在现有 `index.vue` 基础上抽出统一事件分发层，分为以下通道：

- `luna-status`
  更新底部输入条状态文案。
- `APPROVAL_REQUEST`
  更新审批弹窗状态，并写入审批队列。
- `APPROVAL_RESULT`
  给审批队列结果态和成功/失败提示。
- `WORKFLOW_ASYNC_RESULT` / `SKILL_ASYNC_RESULT`
  写入异步任务区与提示。
- `PLAN_*`
  写入 `usePlanGraphStore`。

#### 2.2 发送消息

- 触发位置：
  `ChatInput` 发送按钮和回车。
- 请求前校验：
  `userInput.trim()` 非空。
- 请求：
  `POST /luna/api/chat/message`。
- 成功分支：
  正常回复时，按现有 `normalizeResponse -> handleModelReply` 渲染。
- 挂起分支：
  若回参 `status=pending`，立即显示“任务执行中”文案，并继续依赖 SSE 等待异步结果。
- 审批分支：
  若回参 `status=pending_approval` 或 SSE 收到 `APPROVAL_REQUEST`，打开审批弹窗。
- 失败分支：
  `400` 纯文本 `empty input` 直接映射为输入错误；
  `503 context_governance_blocked` 显示治理阻断文案；
  其他错误按网络失败处理。

#### 2.3 审批弹窗

审批弹窗保留现有 `ApprovalModal.vue`，但必须调整对接规范：

- 展示字段：
  `toolName` 优先展示；
  若缺失则回退 `skillName`；
  `serverCode`、`status`、`taskId` 作为辅助信息；
  `argsJson` 按对象和原始 JSON 双视图展示。
- 倒计时：
  沿用 10 分钟 TTL 逻辑。
- 提交流程：
  点击同意/拒绝后调用 `POST /mcp/tools/approval`，请求体只传布尔值 `approved`，不传数字或字符串。
- 成功展示：
  若回参带 `reply`/`emotion`，直接走聊天回复渲染链路；
  若只返回错误对象或 `raw`，显示系统提示并关闭弹窗。
- 失败展示：
  保留弹窗关闭后的全局提示，不要无限重试。

### 3. 历史记录方案

- 历史面板继续复用 `HistoryPanel.vue`。
- 先调 `GET /luna/api/chat/history/date?ym=yyyy:MM` 得到可点日期。
- 点击某日后调 `GET /luna/api/chat/history?ymd=yyyy:MM:dd`。
- 前端解析格式必须保持现有 `ROLE:content:time` 规则，兼容无时间与异常行。
- 当当前聊天进行中时，若历史面板开启，可在本地先插入用户消息，回复完成后调用 `refresh` 补齐真实历史。

### 4. 计划中心方案

计划中心继续复用现有 `PlanPanel.vue` 与 `usePlanGraphStore.js`，但要按接口文档强化字段使用：

- 创建计划使用 `POST /luna/api/plan/run`，请求体至少传 `userGoal`。
- 计划执行后立即记住 `planId`，并调用 `GET /luna/api/plan/graph/{planId}` 获取首次快照。
- 后续所有 `PLAN_*` 事件先按 `planId` 过滤，再应用到当前计划图。
- `PLAN_FINISHED`、`PLAN_REPORT_READY`、`PLAN_NODE_FAILED` 等关键事件后要触发一次快照补拉，避免事件丢失造成图谱状态漂移。
- 报告生成入口：
  若后端已在主执行链路返回 `reportResult`，直接展示；
  若未返回或需要补生成，再手动调 `POST /luna/api/plan/report/finalize`。

页面展示重点：

- 顶部摘要卡展示 `planId`、`status`、`message`、更新时间。
- 中部按 phase 列展示节点卡片。
- 下部展示边关系、异步技能事件、报告入口。
- 失败节点突出显示 `failReason`、`errorCode`。

#### 5.1 保留的 tab

- `运行日志`
  对接 `POST /luna/api/query/log`

#### 5.2 移除的 tab

  旧接口已退役，前端不再展示。

#### 5.3 现有表格能力复用

但需要调整：

### 6. MCP 能力中心方案

当前 Settings 内的 ToolManager/SkillManager 不适合继续扩展，因为：

- 列表读取已经走 `Resource` 统一视图；
- 写入却仍依赖退役接口；
- 表单字段仍围绕旧 `beanName/methodName` 设计，无法覆盖新的目录、实现映射、服务注册等能力。

因此建议把 Tool/Skill 管理升级为独立的 `CapabilityCenterPanel`。

#### 6.1 页面结构

- 左侧一级导航：
  `资源总览`、`工具目录`、`Prompt 目录`、`资源目录`、`工作流模板`、`服务注册表`、`实现映射`、`JSON-RPC 调试`
- 中间列表区：
  卡片或表格切换
- 右侧详情/编辑抽屉：
  按资源类型展示 Schema、标签、版本、描述与原始 JSON

#### 6.2 接口使用规则

- 总览与搜索：
  首屏调用 `GET /mcp/resources`；
  顶部搜索调用 `POST /mcp/search`。
- 工具调试：
  先 `GET /mcp/tools/list`；
  选择工具后显示 `inputSchema/outputSchema`；
  点击调试调用 `POST /mcp/tools/call`。
- Prompt/资源调试：
  分别调用 `/mcp/prompts/list` + `/mcp/prompts/get`、`/mcp/resources/list` + `/mcp/resources/read`。
- 管理写入：
  所有后台写入统一走 `/mcp/migrate/*`；
  不再使用 `/mcp/tools`、`/mcp/skills`。
- 协议调试：
  `JSON-RPC` 面板可以作为高级模式，直接构造 `/mcp/rpc` 请求体。

#### 6.3 前端职责

- Schema 字段支持对象和 JSON 文本双向展示。
- `serverCode` 缺省时，UI 提示将使用本地默认服务，不在前端手工补写固定值。
- 写入表单提交前只做字段必填与 JSON 可解析校验，不自行模拟后端枚举逻辑。
- 写入成功后必须重新拉当前列表，而不是局部假写。

### 7. Prompt 治理中心方案

Prompt 治理模块体量大，不适合塞进现有 SettingsPanel tab，建议新建独立 `PromptGovernancePanel`。

#### 7.1 页面结构

推荐三栏式结构：

- 中栏：

- 右栏：

右侧再配套三个抽屉：

- 差异对比抽屉
- 预览抽屉

#### 7.2 模块拆分

Prompt 治理中心分四个子域：

1. 分类管理
   使用 `/categories`、`/categories/detail`、`/categories/tree`
2. 条目管理
   使用 `/search`、`/detail`、`/detail-by-id`、`/exists`、`/create`、`/update`、`/save`、`/delete`
3. 版本管理
   使用 `/versions`、`/version/detail`、`/activate`、`/rollback`、`/draft`、`/archive`、`/diff`
4. 预览与策略
   使用 `/preview/match`、`/preview/assemble`、`/policy/*`

#### 7.3 表单交互规则

- 新建前先用 `/api/prompt/item/exists` 做 key 唯一性校验。
- 详情进入编辑时，默认先拉 `/detail`，右侧表单回填 `PromptItemRecord`。
- 保存按钮有两种模式：
  `正式保存` 调 `update` 或 `save`
  `保存草稿` 调 `draft`
- 执行类 Prompt 若需要只生成草稿而不激活，可走 `previewOnly=true` 的 `update`，但这属于二阶段增强能力，优先级低于显式 `draft`。
- 删除前必须二次确认，并提示“软删除，仅禁用，不会清除历史版本”。
- 版本抽屉中：
  `激活` 调 `activate`
  `回滚` 调 `rollback`
  `归档` 调 `archive`
  `对比` 调 `diff`

#### 7.4 预览交互

- `匹配预览`
  用来检查哪些 Prompt 命中和被拒绝。
- `组装预览`
  用来检查各 runtimeSlot 最终拼装文本，以及 `filteredOutItems`。
- 预览页面必须明确区分：
  `matchedItems`
  `rejectedItems`
  `slotMapping`
  `assembled`
  `sectionAssembled`
  `filteredOutItems`

## 前端实现思路

### 1. 保持单路由壳层，不拆后台站点

当前项目只有一个 `/index` 主路由，这和 Electron 桌宠壳层是匹配的。后续不建议新增独立后台路由，而是继续沿用“主壳 + 浮层面板”的组织方式。

### 2. 以“当前可用能力修正 + 新管理面板扩展”双线推进

- 第一条线修正当前已经可见的入口：
  审批、查询中心、Tool/Skill 管理、会话关闭。
- 第二条线扩展新的管理与调试能力：
  MCP 能力中心、Prompt 治理中心、RAG 调试。

### 3. 所有接口统一走 Electron Bridge

后续所有接口都应遵循同一链路：

- `src/api/` 暴露 renderer 侧调用方法
- `electron/preload.js` 暴露安全 API
- `electron/main.js` 或 `src/main/ipc/*.js` 负责真正请求
- `src/main/httpClient.js` 负责 token 注入与 axios 实例

不新增直连 axios 的第三套实现，不扩展 `src/utils/request.js`。

### 4. 保留原始字段，单独做 UI 映射层

因为后端响应结构并不统一，前端需要区分“原始 DTO”和“展示模型”：

- 原始 DTO 只用于严格对齐接口字段。
- 展示模型只做前端渲染友好的组合，不改后端字段名。

例如审批卡片可以显示“操作名称”，但底层数据仍保留 `toolName` 和 `skillName` 原字段，不在 API 层做字段改名。

### 2. 关键交互流程设计

#### 2.1 登录到聊天可用

1. 用户输入账号密码。
2. 调 `/auth/login`。
3. 主进程保存 token。
4. 自动启动 SSE。
5. 进入 boot 动画。
6. 调 `/luna/api/chat/startup`。
7. 渲染欢迎回复。

#### 2.2 聊天与审批

1. 用户发送消息，调 `/luna/api/chat/message`。
2. 底部状态条开始显示流转状态。
3. 如需审批，SSE 收到 `APPROVAL_REQUEST`。
4. 弹出审批卡片。
5. 用户点击同意/拒绝，调 `/mcp/tools/approval`。
6. 成功后将回参继续渲染为聊天回复，或等待后续 SSE 补充结果。

#### 2.3 计划执行

1. 用户输入 `userGoal`。
2. 调 `/luna/api/plan/run`。
3. 取回 `planId`。
4. 立刻拉 `/luna/api/plan/graph/{planId}`。
5. 持续消费 `PLAN_*` 事件更新图谱。
6. 结束后展示报告入口。

#### 2.4 Prompt 编辑

1. 左侧分类树筛选。
2. 中栏 `/api/prompt/search` 拉列表。
3. 点击条目后 `/detail` 拉详情。
4. 编辑时先做 `/item/exists` 或 key 格式校验。
5. `正式保存` 调 `update`/`save`。
6. `保存草稿` 调 `draft`。
7. 打开版本抽屉查看历史。
8. 必要时做 `diff`、`activate`、`rollback`、`archive`。

#### 2.5 RAG 调试

1. 输入 query 与可选上下文。
2. 调 `/luna/api/rag/retrieve`。
3. 展示 `rewrittenQuery` 与命中路由。
4. 分来源展示 evidences。
5. 以 JSON 形式展示 `meta` 调试字段。

## 美化设计

### 1. 视觉统一原则

- 不新增脱离现有主题系统的新色板。
- 所有新面板继续使用 `useTheme.js` 已有 CSS 变量。
- 面板背景沿用 `--bg-panel`、边框沿用 `--border`、文本沿用 `--text-main`。

### 2. 布局样式

- 大型管理面板使用和 Query/Plan 相同的固定定位浮层壳。
- 保持圆角、透明渐变、描边、内发光。
- 复杂页面优先采用“三段式”布局，而不是长表单一路向下滚。

### 3. 卡片、表格、表单样式

- 列表优先卡片化展示核心资源信息：
  名称、类型、版本、状态、描述。
- 详情与编辑区采用“标签 + 输入控件 + 辅助说明”模式。
- Schema 与 JSON 字段统一使用等宽预览区。
- 表格延续 QueryPanel 的可展开长文本策略。

### 4. 按钮层级

- 主操作：
  霓虹主色实底或高亮描边，例如“保存”“执行”“同步目录”“激活版本”。
- 次操作：
  低对比描边，例如“取消”“刷新”“查看详情”。
- 危险操作：
  红色系，例如“删除”“拒绝审批”“归档当前活动版本”。

### 5. 字段展示优先级

- 审批卡片：
  优先展示 `toolName/skillName`、`serverCode`、`argsJson`。
- MCP 能力卡片：
  优先展示 `type`、`name`、`version`、`requiresApproval`、`sensitivity`。
- Prompt 列表：
  优先展示 `key`、`name`、`category/subCategory`、`runtimeSlot`、`enabled`、`version`。
- RAG 调试：
  优先展示 `rewrittenQuery`、证据来源、`score`、`role`、`latency_ms`。

### 6. 空状态、加载态与成功失败反馈

- 空状态：
  使用短句式系统文案，例如“暂无资源”“暂无匹配 Prompt”“暂无证据命中”。
- 加载态：
  保留当前项目的终端风格 loading，不引入骨架屏大改。
- 成功反馈：
  面板内 toast + 全局轻提示双通道。
- 错误反馈：
  表单错误原位展示；
  请求失败面板内展示；
  不使用浏览器原生 `alert` 作为主要交互。

## 数据流与状态设计

### 1. 会话与鉴权数据流

- token 只在主进程 `httpClient` 中作为请求头来源。
- renderer 侧只维护“当前是否登录”“当前会话是否可用”的展示状态。
- 不把 token 写入 `localStorage`。

### 2. SSE 数据流

- SSE 是全局单连接。
- 全局流进入 `useLunaStreamStore`。
- 再分发给聊天状态、审批模块、异步任务区、计划图谱。

### 3. MCP 与 Prompt 数据流

- MCP 资源先保存原始 `Resource`。
- 页面上再按 `type` 做二次分组。
- Prompt 列表保存搜索条件与当前列表。
- 详情与版本分开缓存，避免切换列表时丢失右侧编辑上下文。

### 4. RAG 数据流

- 请求表单状态单独维护。
- 查询结果按四块保存：
  `summary`
  `evidences`
  `roleGroups`
  `meta`
- `meta` 保留原样对象，方便开发和联调阶段直读。

## 异常与边界处理

| 场景 | 触发条件 | 前端处理 |
| --- | --- | --- |
| `401 unauthorized` | token 失效、缺失、被吊销 | 统一回到登录态，清空会话 UI |
| `shutdown` 无响应体 | `/luna/api/chat/shutdown` 成功 | 静默成功，不进入聊天回复渲染 |
| 查询接口 `410` | 调用退役 memory/preference API | 页面不再暴露入口；若收到 410，显示“接口已退役” |
| MCP 旧写接口 `410` | 调用 `/mcp/tools`、`/mcp/skills` | 不重试，提示需迁移到新目录接口 |
| `chat/message` 返回纯文本 | 空输入时 `empty input` | 直接提示输入为空 |
| `context_governance_blocked` | chat/startup 被治理阻断 | 原位展示阻断原因 |
| `pending_approval` | 聊天过程进入审批 | 打开审批弹窗并冻结重复发送 |
| SSE 断开 | 网络波动、服务端断流 | 自动重连，重连成功后补拉当前计划快照 |
| 审批过期 | 倒计时结束或后端任务失效 | 自动关闭弹窗并提示审批已过期 |
| Resource 详情为空 | `/mcp/resources/{id}` 返回 `null` | 详情抽屉显示“资源不存在或已被移除” |
| Prompt 搜索无分页元数据 | `/api/prompt/search` 只返回数组 | UI 采用弱分页，不显示总页数 |
| Prompt 保存限制 | 创建内容类/执行类边界、key 前缀不一致 | 提交前做前端校验，失败后按后端 message 原样展示 |
| Prompt 策略保存 | 每次保存都会新建 active 版本 | 保存成功后必须刷新策略详情与版本列表 |
| RAG 空 query | `400` 空响应体 | 提交前前端拦截空 query |
| RAG 治理拒绝 | `422` 返回 `meta.status=rejected` | 显示治理拒绝原因，不视作网络异常 |
| `/api/luna/status/disconnect` 需鉴权 | 退出登录流程中 token 已清 | 断流必须放在清 token 之前 |

## 风险点与注意事项

1. 后端成功响应没有统一包裹体，前端不能默认所有接口都返回 `{ data, code, message }`。
2. Prompt 模块字段多、限制多，前端只能做“明确已知”的校验，不能自行推断未写在文档中的规则。
3. `toolSlots`、`inputSchema`、`outputSchema`、`argumentsSchema` 可能在不同接口里以对象或字符串出现，展示层必须同时兼容。
4. `APPROVAL_REQUEST` 事件里同时存在 `skillName` 和 `toolName`，展示时要按优先级兼容，而不是提前删字段。
5. 计划事件与异步事件共用一条 SSE，必须始终按 `eventType` 和 `planId` 双重过滤。
6. Prompt 搜索接口没有总数与总页数，页面设计不能强依赖传统分页组件。
7. Prompt 策略保存每次都会生成新版本，列表与详情必须在保存后重新拉取，不能只本地改字段。
8. Electron 透明窗口对大体量 JSON diff、长列表和多面板叠加更敏感，复杂面板默认应支持全屏并控制同时打开数量。
9. 当前项目的核心竞争力是“桌宠 + 运维面板”的一致体验，新模块再复杂，也必须继续保持这一套视觉语言和交互惯性。
