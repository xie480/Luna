# 项目亮点汇总

> 本文档提炼自 Luna 项目代码与设计文档，面向简历呈现的项目亮点。每条亮点均采用简历风格标题，说明业务价值、核心实现机制以及带来的工程能力。

---

## 1. 基于 MCP 的动态工具路由与能力热插拔机制 (Dynamic MCP Tool Routing)

**技术栈**: Spring Boot, PostgreSQL + pgvector, LangChain4j, Java 17

**亮点命名**: 动态 MCP 工具路由与能力热插拔

**亮点说明**
- 通过 `mcp_tool_catalog` 与 `mcp_tool_impl_mapping` 将原有 Bean 反射调用抽象为统一的能力目录，使工具可在运行时跨服务发现、版本化管理。
- `McpClientAdapter` 在 Host 侧统一调用 MCP Server `tools/call`，实现协议层解耦、统一 schema 校验与审批拦截。
- `ToolExecutionGateway` 负责审批、输入校验、审计日志写入，确保高风险工具必经审批流程。

**实现思路**
- 在 `mcp_tools` 表新增 `mcp_tool_catalog`（id、tool_name、input_schema、output_schema、requires_approval、sensitivity、embedding）和 `mcp_tool_impl_mapping`（impl_type、bean_name、method_name）两张表。
- 启动时扫描本地 Spring Bean，自动注册到 `mcp_tool_impl_mapping`，并将公开能力写入 `mcp_tool_catalog`（向量化搜索支持快速检索）。
- `McpClientAdapter.listTools(serverCode)` 通过 `SELECT * FROM mcp_tool_catalog WHERE server_code = ?` 拉取可用工具列表。
- `McpClientAdapter.callTool` 将 JSON 参数发送至 MCP Server，实现统一的 `toolName` + `argumentsJson` 调用入口。
- `ToolExecutionGateway.executeTool` 包装调用流程：审批检查 → schema 校验 → 调用 `McpClientAdapter.callTool` → 记录 `tool_execution_trace`。

**请求流程**
```
User Query → StateDrivenContextPipeline → MCP Candidate Retrieval → ToolExecutionGateway (approval + schema) → MCP Server tools/call → Tool Result → ContextSnapshot → Main Model
```

**亮点价值**
- 实现工具能力的 **即插即用**，新增工具仅需在数据库添加条目，无需代码改动。
- 统一 **风险敏感度** 与 **审批流程**，满足企业合规要求。
- 通过 pgvector 向量索引实现 **语义快速检索**，提升工具匹配精度与响应速度。

## 2. 四类检索流水线的语义分层路由与证据标准化 (Four‑Pipeline RAG Engine)

**技术栈**: PostgreSQL + pgvector, Java, LangChain4j, Spring Data JPA

**亮点命名**: 四层 RAG 流水线 + 统一 Evidence 对象

**亮点说明**
- 将检索任务分为 `Search`, `Native`, `Modular`, `Agentic` 四条流水线，`RouteSelector` 根据查询特征（精准查找、复杂分析、单/多源）进行 **硬路由**，保证最小化检索成本。
- 所有数据源（knowledge, memory, preference）统一映射为 `Evidence`，并在 `Retriever`、`Ranker`、`Fusion` 阶段提供 **源内 Rerank** 与 **跨源 Fusion**，输出结构化证据集合。
- `Evidence` 包含 `id`, `source`, `score`, `metadata`，供上层 `ContextAssembler` 直接使用，避免二次解析。

**实现思路**
- `RouteSelector.selectRoute(query, queryType, sourceCount)` 实现硬路由规则（示例代码位于 `src/main/java/org/yilena/luna/rag/router/RouteSelector.java`）。
- `RetrievalServiceImpl.retrieve(request)` 调用对应 `Pipeline`（如 `ModularPipeline`），在 `retrievers` 中并行调用 `KnowledgeRetriever`, `MemoryRetriever`, `PreferenceRetriever`。
- 每个 `Retriever` 实现 `BaseRetriever.retrieve`，返回 `List<Evidence>`，内部先做 **Embedding 检索** 再 **FTS** 辅助。
- `Ranker` 对同源证据做 `knowledge_score = 0.60*vector + 0.25*fts + ...`（参考 `docs/rag.md`），随后 `EvidenceFusionService` 合并、去重、压缩。

**请求流程**
```
User Query → QueryProcessor → Router → Selected Pipeline → Parallel Retrievers → Source‑Rerank → Fusion → Dedup → Compression → RetrievalResponse (Evidence)
```

**亮点价值**
- **检索成本可预测**：硬路由保证高精度查询不走全流水线。
- **证据统一**：`Evidence` 为上层上下文提供结构化、可审计的输入，支持 **上下文快照** 与 **回放**。
- **多源协同**：一次检索即返回知识、记忆、偏好三类证据，提升任务理解与生成质量。

## 3. 双域分层记忆架构与即时写回管线 (Dual‑Domain Layered Memory)

**技术栈**: PostgreSQL, pgvector, Redis, Java

**亮点命名**: 双域分层记忆 + 任务/关系双状态机

**亮点说明**
- 将记忆拆分为 **任务域** 与 **关系域**，每域拥有 Working、Semantic、Episodic、Procedural 四层，分别存储短期上下文、长期事实、经验模式与过程化规则。
- `MemoryHotLayerService` 在 Redis 中缓存最近 `task_working_memory` 与 `relational_working_memory`，实现亚毫秒读取，用于 **输入重构** 与 **上下文裁剪**。
- `MemoryWritePipeline` 在每轮对话结束后，按照 `Message Writer → State Updater → Working Memory Updater → Semantic Extractor → Episode Builder → Reflection Trigger → Procedure Miner → Registry Updater` 流程，将新事实写入对应层级并生成 **可审计的记忆事件**（`memory_event_log`）。

**实现思路**
- 表结构见 `docs/memory.md`：`task_working_memory`, `task_semantic_fact`, `relational_semantic_fact` 等表均配备 `embedding` 向量列，用于向量检索。
- `RuntimeRetriever` 在查询时根据 `TaskState`、`RelationalState` 动态选择对应 `MemoryRetriever`（`TaskMemoryRetriever` / `RelationalMemoryRetriever`），返回结构化记忆块。
- `MemoryHotLayerService` 在写入时将最新 Working Memory 写入 Redis，并在事务提交后批量落库，确保 **强一致性 + 高吞吐**。

**请求流程**
```
User Input → InputReconstructionAgent → RetrievalState (RAG) → MemoryRetriever (Task & Relation) → ContextAssembler → Main Model → Model Output → MemoryWritePipeline → Redis Cache + PG写入 → State Store Update
```

**亮点价值**
- **任务‑关系同步**：双状态机驱动记忆读取，使情感/关系信息与任务指令保持一致，提升对话连贯性。
- **低延迟记忆**：热层 Redis 缓存实现毫秒级记忆访问，满足实时上下文需求。
- **可审计记忆**：每条记忆写入伴随 `memory_event_log`，支持事后回放与根因分析。

## 4. 小型 Agent 驱动的上下文治理流水线 (Small‑Agent Context Governance)

**技术栈**: Java, Spring, LangChain4j

**亮点命名**: 输入重构 + 全局重排 + 结果语义化小 Agent

**亮点说明**
- `InputReconstructionAgent` 将原始用户输入、短期记忆、任务状态统一 **结构化为意图**（`normalizedUserIntent`、`missingSlots` 等），解决单轮输入信息不足导致的检索噪声问题。
- `GlobalContextRerankAgent` 在所有候选证据（RAG、MCP、Memory）上执行 **节点感知语义重排**，确保仅与当前 `TaskState`、`RelationalState` 相关的证据进入工作集。
- `ToolSemanticAgent` 对工具原始返回做 **语义抽取 + 结构校验**，生成 `toolStatus`, `keyFacts`, `nextStepHint`，并通过双通道写入：原始日志 + 语义化上下文。
- `SummaryAgent` 基于全量短期记忆生成 **双摘要**（Narrative Summary + State Snapshot），供后续节点使用，避免信息遗漏。

**实现思路**
- `DefaultInputReconstructionAgent`（`src/main/java/org/yilena/luna/context/impl/DefaultInputReconstructionAgent.java`）读取 `StructuredContextPackage`，使用规则模板生成 `InputReconstructionResult`。
- `DefaultGlobalContextRerankAgent`（`src/test/java/.../DefaultGlobalContextRerankAgentTest.java`）实现 `rerank(evidences, taskState, relationalState)`，返回排序后的 `Evidence` 列表。
- `DefaultToolSemanticAgent` 将 `toolName`、`rawResult` 与当前 `TaskState` 结合，输出 `ToolSemanticResult`（结构化 JSON），并写入 `tool_execution_trace` 表。
- `DefaultSummaryAgent` 读取 `task_working_memory` 与 `relational_working_memory`，生成两段摘要后写入 `summary` 表与 `ContextSnapshot`。

**请求流程**
```
User Input → InputReconstructionAgent → RetrievalState (RAG) + RetrievalState (MCP) → GlobalContextRerankAgent → ContextAssembler → Main Model → Tool Call → ToolSemanticAgent → MemoryWritePipeline → State Update
```

**亮点价值**
- **语义保持的裁剪**：通过小 Agent 前置处理，仅保留真正对当前节点有价值的信息，显著降低 token 消耗。
- **统一治理**：所有关键转化（意图、证据、工具结果、摘要）均在小 Agent 中完成，避免冗余实现，提高可维护性。
- **审计友好**：每一步都有独立日志与快照，支持完整回放与根因追踪。

## 5. Prompt Registry 与酒馆式分类治理 (Prompt Registry & Tavern‑Style Management)

**技术栈**: PostgreSQL, Spring Data JPA, Java

**亮点命名**: PostgreSQL 真源 Prompt Registry + 版本化酒馆式管理

**亮点说明**
- 将所有 Prompt 资产抽象为 `prompt_item` 表，统一 **分类、子分类、runtimeSlot、模板变量、assemblyMode、版本、编辑策略** 等元数据。
- 内容型 Prompt（persona、scene、style 等）支持 **热新增、删除、关键字匹配**，执行型 Prompt（tool、repair、summary 等）仅 **可编辑、不可删除**，由 `editPolicy` 强制治理。
- `PromptResolver` 根据运行时 `agent`, `nodeKind`, `taskState`, `matchKeywords` 动态匹配 Prompt，输出 `matchedItems` 并映射到 `DefaultContextAssembler` 的 `runtimeSlot`，实现 **动态装配** 而不改动主链路代码。
- 快照 `FINAL_MODEL_CONTEXT` 增加 `promptItemId`, `promptKey`, `promptVersion`，实现 **Prompt 级回放** 与 **版本回滚**。

**实现思路**
- 表结构见 `docs/prompt/prompt架構設計.md` 中的 `prompt_item` JSON 示例；实际建表使用 `prompt_item`、`prompt_item_version` 两张表。
- `PromptRegistryService` 提供 `listCategories()`, `listItems(category)`, `getItemDetail(key)`, `saveItem(itemDto)` 等 CRUD 接口。
- `PromptResolverService` 接收 `ResolverRequest`（sessionId, agent, nodeKind, taskState, userInput），先进行 **关键字匹配**（`keywordMatchEnabled`），再进行 **Agent‑Only** 与 **Policy‑Only** 匹配，返回 `PromptMatchResult`（包含 `runtimeSlot`）。
- `DefaultContextAssembler` 在组装阶段改为读取 `PromptResolver` 返回的 Prompt 列表，按 `runtimeSlot` 填入对应 Section（如 `instructions.persona`、`tool.evidence` 等）。

**请求流程**
```
User Input → InputReconstructionAgent → PromptResolver (category + match) → Prompt Items → ContextAssembler (section mapping) → Main Model → Model Output
```

**亮点价值**
- **统一真源**：所有 Prompt 从数据库统一读取，代码不再硬编码 Prompt 文本，提升可维护性。
- **版本化 & 回滚**：支持 `draft/active/archived` 三状态，快速切换、滚动回滚，满足生产级安全要求。
- **酒馆式编辑体验**：前端可按分类浏览、关键词搜索、热修改，极大提升运营效率。

## 6. 双状态机驱动的任务与关系协同对话流 (Dual‑State Machine Dialogue Flow)

**技术栈**: Java Enum State Machine, Spring State Store

**亮点命名**: 关系‑任务双状态机驱动的对话协同

**亮点说明**
- `TaskRuntimeState` 与 `RelationalRuntimeState` 两套状态机分别管理任务进度（IDLE、UNDERSTANDING、PLANNING、EXECUTING、REPLANNING、COMPLETED）与情感关系（COLD_START、TRUST_BUILDING、EMOTIONAL_SUPPORT、REPAIRING）。
- `StateDrivenContextPipelineImpl` 每轮根据 **双状态** 读取 `TaskStateStore` 与 `ContextStateStore`，决定 **检索策略**、**Prompt 组合** 与 **是否进入情感安抚分支**。
- 当检测到 **情感突发**（如用户表达低落）时，状态机自动切换至 `EMOTIONAL_SUPPORT`，触发 `SocialReasonerService` 生成情感支持 Prompt，随后恢复任务流。

**实现思路**
- 状态实体 `TaskState`、`RelationalState` 均持久化至 PostgreSQL (`task_state`、`relational_state` 表) 并在 Redis 中缓存最新状态。
- `StateDrivenContextPipelineImpl.handleRound(RoundPipelineRequest)` 读取两套状态，调用对应的 `Agent`（`InputReconstructionAgent`、`GlobalContextRerankAgent`、`SocialReasonerService`）并在 `ContextAssembler` 中加入对应 Section（如 `social.empathy`）。
- `TaskOrchestratorServiceImpl` 在任务节点结束后调用 `StateTransitionLog` 记录状态迁移，支持 **审计追溯**。

**请求流程**
```
User Input → StateDrivenContextPipeline (读取 TaskState + RelationalState) → 选择检索 / 社交 Agent → PromptResolver → ContextAssembler → Main Model → 结果 → StateTransitionLog → 新状态写回
```

**亮点价值**
- **任务‑情感融合**：同一轮对话既能推进业务任务，又能实时提供情感陪伴，提升用户满意度。
- **可观测状态迁移**：每次状态切换记录日志，便于事后分析与模型调优。
- **灵活中断恢复**：状态机决定是否进入 `WAITING_APPROVAL`、`WAITING_USER` 等中间态，支持 **审批中断** 与 **任务恢复**。

## 7. OpenClaw 风格的计划‑执行 DAG 编排与自动重规划 (OpenClaw‑Style DAG Orchestration)

**技术栈**: Spring Batch‑like DAG Engine, PostgreSQL, Java

**亮点命名**: DAG 计划‑执行 + 自动重规划机制

**亮点说明**
- `plan_instance`, `plan_phase`, `plan_node`, `plan_edge` 表构成 **有向无环图（DAG）**，`PlanOrchestratorServiceImpl` 负责 **阶段调度**、**节点并行/串行**、**失败重试** 与 **局部重规划**（`replan_failed_nodes`）。
- 每个 `plan_node` 通过 `capability_type`（TOOL / PROMPT / RESOURCE / WORKFLOW）指向具体执行对象，配合 `CapabilityCatalogService` 动态解析。
- `PlanCheckpoint` 与 `PlanEventLog` 实现 **检查点快照**，在中断或异常后可 **快速恢复** 到最近节点。

**实现思路**
- `PlanOrchestratorController` 接收外部 `PlanBlueprint`，生成 `plan_instance` 并拆分为 `plan_phase` 与 `plan_node`（依据 `plan_node.node_type`）。
- `PhaseExecutionServiceImpl` 按 `phase_id` 调度节点，支持 `parallel` 与 `sequential` 两种执行模式。
- 节点执行失败后，`PlanEventLog` 记录 `FAILURE`，`ReplanService` 根据 `failureReason` 触发 **局部重规划**，仅重新计算受影响的子图。
- `PlanCheckpoint` 在每个关键节点完成后保存 `ContextSnapshot`，用于 **断点续跑**。

**请求流程**
```
Plan Blueprint → PlanOrchestratorService → DAG 构建 → PhaseExecutionService (调度) → Node Execution (Tool/Prompt) → EventLog / Checkpoint → (Failure?) → Replan Service → 新 DAG → 继续执行 → 完成 → Report
```

**亮点价值**
- **可视化可编排**：通过 DAG 明确任务依赖，便于业务分析与调度优化。
- **自动重规划**：仅重算失败子图，显著降低整体重跑成本。
- **检查点恢复**：在长任务或审批中断场景下，能够 **秒级恢复**，提升系统可靠性。

## 8. Token 预算分层裁剪与语义保持型上下文组装器 (Token‑Budgeted Semantic‑Preserving Context Assembler)

**技术栈**: Java, Spring, LangChain4j, Redis

**亮点命名**: 分层 Token 预算 + 语义保持裁剪

**亮点说明**
- `ContextAssembler` 将所有候选上下文（Instructions, Task State, Reconstructed Intent, Knowledge Evidence, MCP Hints, Tool Evidence, Recent Interaction, Memory Hints, Output Constraints）划分为 **固定分区**，为每个分区配置独立 **Token 上限**。
- `ContextPruner` 在裁剪时仅执行 **去重、聚类合并、字段抽取、模板化压缩**，绝不截断关键数值或约束，保证 **语义完整性**。
- 通过 `SemanticPreservingPruner`（实现位于 `src/main/java/org/yilena/luna/utils/ContextPruner.java`）实现 **分层优先级裁剪**（优先保留 `Instructions`、`Current Task State`），并在必要时触发 **摘要替换**（双摘要）。

**实现思路**
- `StateDrivenContextPipelineImpl.buildContext()` 为每个 Section 填充内容，并调用 `ContextPruner.prune(sectionContent, tokenBudget)`。
- `ContextPruner` 计算每段的 token 长度（使用 `LlmClientUtil.estimateTokens`），若超预算则执行：① 去重相似 Evidence；② 合并相邻 Memory 片段；③ 对长文本执行 `summary`（调用 `SummaryAgent`）；④ 保留关键字段（如 `deadline`, `budget`, `taskId`）。
- 裁剪规则统一存于 `context_prune_rules.yaml`，可热更新。

**请求流程**
```
All Candidates → Section Mapping → Token Budget Allocation → ContextPruner (per section) → Final Workset → Main Model
```

**亮点价值**
- **高效 Token 使用**：显著降低模型调用成本，保证在模型上下限内完成复杂任务。
- **语义不丢失**：通过摘要与结构化压缩，关键业务信息始终保留，提升模型生成准确性。
- **可配置裁剪**：运维可调节每个 Section 的 token 配额，灵活适配不同模型（12k/32k 等）。
