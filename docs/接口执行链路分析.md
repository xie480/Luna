# Luna 项目接口执行链路分析

## 1. 分析范围与代码基线
- 分析代码：`src/main/java`、`src/main/resources`
- 覆盖入口类型：Controller HTTP、SSE、MCP REST/JSON-RPC、Prompt 治理、审批恢复、兼容别名、退役接口
- 统一链路组件：`RequestCachingFilter`、`AuthInterceptor`、`GlobalExceptionHandler`、`LunaLogAspect`
- 说明原则：只写源码里真实发生的执行顺序，不写抽象模板

---

## 2. 统一入口链路影响（多数接口共用）

### 2.1 请求包装（`RequestCachingFilter`）
1. 请求进入 Filter 后会被包装为 `ContentCachingRequestWrapper`。
2. 这样在异常处理阶段可以再次读取原始 request body。
3. `/api/luna/status/stream` 明确跳过包装，避免干扰 SSE 长连接。

### 2.2 鉴权注入（`AuthInterceptor`）
1. `WebMvcConfig` 把拦截器挂到 `/**`。
2. 白名单放行：`/auth/login`、`/api/luna/status/stream`、Swagger/OpenAPI 路径。
3. 其余请求读取 `Authorization`，调用 `AuthService.validateToken`。
4. token 合法后再次提取 `jti` 和 `sub`：
   - `jti` 写入 `AuthContextHolder.sessionId`
   - `sub` 归一化后写入 `AuthContextHolder.principalKey`
   - 同时写到 request attribute，供后续链路读取
5. 任一步失败直接返回 `401` JSON，不进入 Controller。

### 2.3 全局异常（`GlobalExceptionHandler`）
1. `AuthException` -> `401`。
2. `NeedApprovalException` -> `200`，返回 `status=pending_approval` + `taskId`，用于前端进入审批流。
3. 其他异常：
   - 读取缓存的 request body 作为 `userInput`
   - 组装 `LunaExceptionContext`
   - 交给 `ExceptionRetryService` 生成兜底响应，HTTP `500`

### 2.4 AOP 日志（`LunaLogAspect`）
1. `@LunaLogRecord` 标注的方法会被 AOP 包裹，统一记录入参、耗时、响应、异常。
2. 日志异步发送 MQ；MQ 不可用时进入 30 秒降级窗口，跳过发送，避免拖慢主链。
3. 聊天链路会通过 `LOG_RESPONSE_OVERRIDE` 覆盖默认响应日志，保证日志记录最终模型输出而不是中间对象。

## 4. 主链路接口（walkthrough 级）

## 4.1 `POST /luna/api/chat/message`

### 接口用途
执行完整一轮对话：输入治理、上下文构建、工具决策、主模型回答、状态写回、记忆写回。

### 执行流程
1. `ChatController.chat` 把 `ChatRequest` 透传到 `ChatServiceImpl.chat`。
2. `ChatServiceImpl` 先提取 `userInput.trim()`，为空直接 `400: empty input`。
3. 发布 SSE 状态：先 `THINKING`，再 `RETRIEVING`。
4. 计算 `runtimeSessionId`：优先 JWT `jti`，没有则用当天 `yyyy:MM:dd`。
5. 先跑一次 `StateDrivenContextPipeline.run(stage=CHAT_PRE_TOOL, runMainModel=false, writeRoundState=false)`，目标是拿到可执行工件，而不是直接问大模型。
6. 如果 pre-tool pipeline 被阻断，或者缺少 `decision/contextPackage/reconstruction/nodeWorkset` 任一工件，直接 `503 context_governance_blocked` 并把 SSE 置回 `IDLE`。
7. 从 `contextPackage/nodeWorkset` 抽取本轮使用的知识片段、偏好片段、长期记忆、工作记忆、最近对话、候选工具、MCP 资源提示。
8. 调 `TaskOrchestratorService.orchestrateToolDecisionNode`：
   - 用治理后的输入构造工具决策输入
   - 生成 `assembledDecisionContext` 与 `governedInputSignature`
   - 交给 `AgentServiceImpl.processToolCallingWithGovernance`
9. `AgentServiceImpl` 在 strict 模式下会硬校验三件事：
   - `assembledDecisionContext` 非空
   - `toolDecisionInput` 非空
   - `governedInputSignature` 可验签
   任一失败都会拒绝工具决策并写审计记录。
10. 工具决策成功后得到 `toolContext`、`toolSemanticResult`、`rawToolResultChannel`（包含 tool trace 引用）。
11. `ChatServiceImpl` 生成 `synthesisBrief`，并把语义化工具结果与原始工具结果融合。
12. 分支 A：若 `toolContext.status=pending`（异步工具场景）
   - 构造 pending 文案（包含 taskId/workflowName）
   - 把 pending 工具任务缓存到 hot layer
   - 运行 memory write gate，达阈值才写记忆
   - 再跑一次 `StateDrivenContextPipeline.run(stage=CHAT_TURN_PENDING, runMainModel=false, assistantReplyOverride=pendingReply, writeRoundState=true)`，把 pending 状态写入轮次状态
   - 返回 pending JSON，SSE 置 `IDLE`
13. 分支 B：普通同步场景
   - SSE 更新为 `THINKING_ORGANIZE`
   - 运行 `StateDrivenContextPipeline.run(stage=CHAT_TURN, runMainModel=true, replaceHistoryWithSummary=true, writeRoundState=true)`
   - pipeline 内部会执行：重构校验 -> 召回/rerank -> context assemble -> 主模型调用 -> summary -> round state writeback
14. 如果 `roundPipelineResult` 或 `mainModelResult` 被阻断，返回 `503 context_governance_blocked`。
15. 成功时：
   - `LOG_RESPONSE_OVERRIDE` 写入原始模型响应，供 AOP 记录
   - 计算 memory write gate，允许才写入 `memoryWritePipelineService.writeAfterTurn`
   - 记录 `QUALITY_REPLAY_COMPARISON` 和 `MEMORY_WRITE_THRESHOLD_GOVERNANCE` 审计
   - SSE 回到 `IDLE`
   - 返回 `modelResult.validResponse`（能解析 JSON 就返回 JSON 节点）

### 关键分支
- 输入为空：`400`
- 治理工件缺失或 pipeline blocked：`503`
- 命中审批/异步工具：返回 `pending`，本轮不跑主模型
- 主模型链路 blocked：`503`

## 4.2 `POST /luna/api/rag/retrieve`

### 接口用途
受治理的检索入口：先做输入治理和 workset 决策，再执行检索。

### 执行流程
1. `RagController.retrieve` 收到 `RetrievalRequest`，`query` 为空直接 `400`。
2. 归一化 `sessionId`：为空时使用固定值 `rag-governed-session`。
3. 先执行 `taskOrchestratorService.orchestrateUserInput(sessionId, rawQuery)`，得到 `decision/contextPackage/reconstruction`。
4. 再执行 `taskOrchestratorService.orchestrateNodeWorkset(...)`，从 workset 中提取治理后的 `ragQuery`。
5. 若 `ragQuery` 为空：
   - 返回 `422`
   - `meta` 里标记 `governed=true,status=rejected,reason=...`
   - 同时回传 `rawQuery/governedQuery/mcpDrivenInput`
6. 若 `ragQuery` 非空：构造新的 `RetrievalRequest`：
   - `query` 用治理后的 `governedQuery`
   - `allowedRoutes/sourceScope` 为空时填全量枚举
   - 透传 `conversationContext/options`
7. 调 `RetrievalServiceImpl.retrieve(governedRequest)`：
   - `QueryProcessor` 先做 query 重写和 queryType 分类
   - `RouteSelector` 选 route/topK/rerank 策略
   - 按 route 选择具体 `RetrievalPipeline` 执行
8. `RetrievalServiceImpl` 在结果 `meta` 中补写 `sources_used/latency_ms/query_type/session_id/needs_rerank`。
9. `RagController` 合并原结果与治理元信息，最终响应始终带 `governed=true + raw/governed query`。

### 关键分支
- 原始 query 为空：`400`
- 治理后 query 为空：`422`（拒绝检索）
- route 对应 pipeline 不存在：返回 empty response（非异常抛出）

## 4.3 `POST /luna/api/plan/run`

### 接口用途
创建并执行完整计划：蓝图生成 -> 相位执行 -> 收尾报告 -> 可选回写聊天。

### 执行流程
1. `PlanOrchestratorController.run` 校验 `userGoal`，缺失返回 `INVALID_REQUEST`。
2. session 选择顺序：JWT `jti` > 请求 `sessionId` > `PLAN_DEFAULT_SESSION_ID`。
3. 调 `PlanOrchestratorServiceImpl.createAndRunPlan(sessionId, userGoal)`。
4. 服务先调用 `taskOrchestratorService.orchestrateBlueprintInput`：
   - 做输入重构，提取 `explicitTaskGoal`
   - 组装 blueprint draft、知识证据、workflow hints
5. 若无法得到 `effectiveGoal`，直接返回 `PLAN_RECONSTRUCTION_REQUIRED`，禁止回退到原始 `userGoal` 盲跑。
6. 创建 `planId` 并插入 `plan_instance`，把重构结果和 blueprint draft 写入 `constraintsJson`。
7. 调 `MasterPlanningService.generateBlueprint`：
   - 构造规划 prompt（goal + reconstructedIntent + knowledgeEvidence + workflowHints）
   - 调规划模型
   - 若模型空响应/解析失败，走 fallback blueprint
8. 调 `BlueprintValidationService.validate` 校验蓝图；失败则更新计划状态 `FAILED` 并返回 `PLAN_BLUEPRINT_INVALID`。
9. 蓝图保存成功后，落库 phases/nodes/edges，并把计划状态改为 `RUNNING`。
10. 写入 blueprint 阶段 round state（`writeRoundState`），把 `blueprintGenerated=true/planId` 等检索计划覆盖信息落到状态仓。
11. 读取 phase 列表按顺序执行；每个 phase 调 `phaseExecutionService.executePhase`：
   - phase 内先做 DAG 拓扑分批
   - 单批内虚拟线程并行执行节点
   - 节点失败或审批挂起都会中断后续批次
12. 所有 phase 结束后执行 `finalizeAndReport(planId)`。
13. 汇总 `phaseResults + reportResult`，根据是否有 phase 失败决定最终状态：
   - 有失败：`status=error`，计划状态 `FAILED`
   - 全成功：`status=success`，计划状态 `SUCCESS`
14. 如果 `callbackToChat=true`，把最终结果主动发送回聊天链路。

### 关键分支
- `effectiveGoal` 缺失：拒绝建图
- blueprint 校验失败：不进入 phase 执行
- phase 执行出现失败：提前终止后续 phase
- phase 出现 pending approval：返回 `PHASE_PENDING_APPROVAL`，等待审批恢复

## 4.4 `POST /mcp/tools/call`

### 接口用途
MCP 工具统一调用入口，负责本地/远端分发与传输协议适配。

### 执行流程
1. `McpController.callTool` 从 body 读取 `serverCode/toolName/argumentsJson`，直接传给 `McpService.callTool`。
2. `McpServiceImpl.callTool` 仅做一层委派到 `McpClientAdapter.callTool`。
3. `LocalMcpClientAdapter.callTool` 先查 `mcp_server_registry` 判定目标服务：
   - 本地（`serverCode=local` 或 transport=LOCAL 或无 baseUrl）
   - 远端（有 baseUrl 且 transport 非 LOCAL）
4. 本地分支进入 `LocalMcpServerServiceImpl.callTool`：
   - 查 `mcp_tool_impl_mapping`，无映射直接返回 `TOOL_MAPPING_NOT_FOUND`
   - 校验 `executionMode` 与 `implType` 组合是否合法
   - 根据 `implType` 分发：
     - `LOCAL_HANDLER` -> 调 `LocalMcpToolHandler`
     - `HTTP/RPC/WORKFLOW` -> 按 routeUri 发 HTTP
     - `SPRING_BEAN` -> 兼容模式，受 `allow-spring-bean` 开关控制
   - 统一解析返回体，组装 `McpToolCallResult(status/rawResult/data)`
5. 远端分支由 `LocalMcpClientAdapter` 按 transport 适配：
   - `HTTP/SSE` 直接 REST
   - `RPC` 封装 JSON-RPC 到 `/mcp/rpc`
   - `WS` 走 WebSocket 单次请求
   - `STDIO` 启子进程收发一行 JSON
6. 远端失败统一转 `errorResult`，并带错误码如 `REMOTE_HTTP_ERROR/REMOTE_RPC_ERROR/REMOTE_WS_TIMEOUT/...`。

### 关键分支
- mapping 缺失
- implType 与 executionMode 不兼容
- 功能开关禁用（`allow-legacy-mode`、`allow-spring-bean`）
- 远端传输层失败

## 4.5 `POST /mcp/tools/approval`

### 接口用途
承接审批中断后的人工确认，继续主链并返回恢复后的聊天结果。

### 执行流程
1. `ApprovalController.submitApproval` 读取 `taskId` 与 `approved`，`approved` 支持 bool/数字/字符串（yes/no/1/0）。
2. 参数不完整或无法解析时返回 `400`。
3. 调 `ApprovalServiceImpl.processApproval(taskId, approved)`。
4. 服务先从 Redis 取任务，未命中再查 DB `approval_task` 并反序列化 payload。
5. 若任务不存在：发布 SSE `IDLE`，返回 error JSON（task not found）。
6. 找到任务后写入审批事件 `eventIngressService.ingestApproval`，让状态机感知本次人工决策。
7. 分支 A（`approved=true`）：
   - 任务状态改为 `RUNNING`
   - SSE 推送 `THINKING`（执行已批准工具）
   - 执行 `executeApprovedTool`（最终走 `McpService.callTool`）
   - 工具结果返回后进入 `continueChatAfterToolDecision(..., approved=true)`
8. 分支 B（`approved=false`）：
   - 不执行工具
   - 直接 `continueChatAfterToolDecision(..., approved=false)`
9. `continueChatAfterToolDecision` 的恢复链：
   - 调 `taskOrchestratorService.orchestrateSystemRecovery(..., recoveryEvent=APPROVAL_RESUME)`
   - 基于恢复后的上下文再次 `orchestrateNodeWorkset`
   - 组装 `RoundPipelineRequest(stage=APPROVAL_RECOVERY, runMainModel=true, writeRoundState=true)`
   - 调 `StateDrivenContextPipeline.run` 继续完成一轮主模型回复
10. 若恢复链 blocked 或异常：
   - 阻断时返回治理失败 JSON
   - 异常时降级 `wrapToolResultAsReply`
11. 恢复成功后：
   - `memoryWritePipelineService.writeAfterTurn`
   - `sessionService.appendMessage` 写回 LUNA 回复
   - 更新审批任务最终状态（`COMPLETED/FAILED/REJECTED`）
12. 删除 Redis 审批键，发送 `approval_result` SSE 事件，最后状态回 `IDLE`。

### 关键分支
- 任务不存在
- 工具执行失败（状态置 `FAILED`）
- 恢复链 blocked
- 恢复链异常降级为工具结果回包

## 5. 其他接口链路（逐接口）

## 5.1 认证

### `POST /auth/login`
1. Controller 读取用户名密码。
2. `AuthServiceImpl.login` 对比配置中的账号密码。
3. 校验通过后签发 JWT（`HS256`，包含 `sub/jti/iat/exp`）。
4. 返回 `{token}`。
5. 用户名或密码不匹配时抛 `AuthException`，由全局异常转 `401`。

### `POST /auth/logout`
1. Controller 读取 `Authorization`。
2. `AuthServiceImpl.logout` 先提取并校验 token 的 `jti`。
3. 将 `jti` 放入内存黑名单 `revokedJti`。
4. 后续同 token 会在 `validateToken` 里被拒绝。

## 5.2 聊天辅助

### `POST /luna/api/chat/startup`
1. 写入一条 `STARTUP` 会话消息。
2. 执行 `StateDrivenContextPipeline.run(stage=STARTUP, runMainModel=true)`。
3. 如果 pipeline 或主模型结果 blocked，返回 `503 context_governance_blocked`。
4. 成功时记录日志覆盖值、追加 LUNA 回复到会话、SSE 回 `IDLE`。

### `POST /luna/api/chat/shutdown`
1. 只写一条 `SHUTDOWN` 会话消息。
2. 不触发模型调用。
3. 返回 `200` 空体。

### `GET /luna/api/chat/history/date`
1. 输入 `ym`，拼接前缀 `ym:`。
2. 前缀过短直接返回空列表。
3. 查询 `session_runtime` 里匹配前缀的 `session_id`。
4. 截取日期尾段返回。

### `GET /luna/api/chat/history`
1. 用 `ymd` 作为会话 key 调 `sessionService.getRecentMessages`。
2. 把消息格式化为 `ROLE:content:time` 字符串数组返回。

## 5.3 Plan 辅助

### `POST /luna/api/plan/phase/run`
1. 校验 `planId/phaseId`。
2. 查 phase 是否存在且属于对应 plan。
3. 调 `PhaseExecutionService.executePhase`。
4. phase 执行成功/失败会更新 phase 状态并推送 phase 进度事件。
5. 返回该 phase 的结构化执行结果 JSON。

### `POST /luna/api/plan/report/finalize`
1. 校验 `planId`。
2. 汇总 plan/phase/node 执行数据。
3. 生成最终报告并更新 plan 完成状态。
4. 返回报告对象（可解析 JSON 则返回 JSON）。

### `GET /luna/api/plan/graph/{planId}`
1. 校验 `planId`。
2. 读取 plan、phase、node、edge。
3. 组装图结构快照返回。

## 5.4 MCP 接口

### `POST /mcp/rpc`
1. 读取 JSON-RPC `id/method/params`。
2. `method` 为空返回 `INVALID_REQUEST`。
3. 根据 method switch 到 `mcpService` 的 list/call/get/read。
4. 结果为空返回 `METHOD_NOT_FOUND`。
5. 统一输出 JSON-RPC 2.0：`jsonrpc/id/result|error`。

### `GET /mcp/resources`
1. `McpServiceImpl.listAll` 聚合 tool/prompt/resource/workflow 四类 catalog。
2. 额外附加 domain resource 模板（knowledge/user/memory/schedule）。
3. 返回统一 `Resource` 列表。

### `GET /mcp/resources/{id}`
1. 依次在 tool/prompt/resource/workflow 表里按 id 查。
2. 命中即转成 `Resource` 返回。
3. 都未命中返回 `null`。

### `POST /mcp/search`
1. 关键词为空直接空列表。
2. 先做 keyword match，再做 embedding 语义检索（最多 20 条）。
3. 两路结果按资源唯一键去重合并返回。

### `GET /mcp/tools/list`
1. `mcpService.listTools(serverCode)`。
2. 适配器按 server registry 决定走本地还是远端。
3. 返回标准 `McpToolDescriptor` 列表。

### `GET /mcp/prompts/list`
1. 调 `mcpService.listPrompts(serverCode)`。
2. 本地走 `LocalMcpServerService.listPrompts`，远端走 transport 适配。
3. 返回 prompt 描述列表。

### `POST /mcp/prompts/get`
1. 读取 `serverCode/promptName/argumentsJson`。
2. 本地分支查 `mcp_prompt_catalog` 并回显参数。
3. 远端分支按 transport 调用并反序列化。
4. 返回 `McpPromptResult`。

### `GET /mcp/resources/list`
1. 调 `mcpService.listResources(serverCode)`。
2. 本地返回 catalog + dynamic template 描述。
3. 远端按 transport 获取并返回。

### `POST /mcp/resources/read`
1. 读取 `serverCode/resourceUri`。
2. 本地优先识别 `resource://` 动态资源：
   - `knowledge/query`
   - `user/preferences/current`
   - `memory/session/current`
   - `schedule/today`、`schedule/task/{id}`
3. 动态命中直接查对应 mapper 返回。
4. 未命中动态则查 `mcp_resource_catalog`。
5. 远端分支走 transport 适配调用。

### `POST /mcp/catalog/sync`
1. 调 `CapabilityCatalogSyncService.syncFromServers()`。
2. 返回 `status=success`，表示已触发同步。

### `POST /mcp/migrate/server-registry`
1. 校验 `serverCode`。
2. 按 `serverCode` 做 upsert。
3. 返回保存后的 registry。

### `POST /mcp/migrate/tool-catalog`
1. 校验 `serverCode/toolName`。
2. 规范化 `executionMode`，补 embedding。
3. 按 `(serverCode,toolName)` upsert。

### `POST /mcp/migrate/tool-impl-mapping`
1. 校验 `serverCode/toolName`。
2. 规范化 `implType/executionMode`。
3. 若 `SPRING_BEAN` 且配置禁用，直接抛参数异常。
4. 按 `(serverCode,toolName)` upsert。

### `POST /mcp/migrate/prompt-catalog`
1. 校验 `serverCode/promptName`。
2. 生成 embedding。
3. 按 `(serverCode,promptName)` upsert。

### `POST /mcp/migrate/resource-catalog`
1. 校验 `serverCode/resourceUri`。
2. 生成 embedding。
3. 按 `(serverCode,resourceUri)` upsert。

### `POST /mcp/migrate/workflow-template`
1. 校验 `workflowName`。
2. 生成 embedding。
3. 按 `workflowName` upsert。

### 退役接口：`POST|PUT|DELETE /mcp/tools*`、`POST|PUT|DELETE /mcp/skills*`
1. Controller 不再进入业务层。
2. 固定返回 `410 Gone` + 升级提示。

## 5.6 SSE

### `GET /api/luna/status/stream`

2. 调 `LunaStatusPublisher.subscribe` 建立默认客户端连接。

### `GET /api/luna/status/disconnect`

2. 返回断开提示字符串。

## 5.7 查询

### `POST /luna/api/query/knowledge-base`（含 `/page`）
1. 空 body 时创建默认查询对象。
2. 归一化分页参数（`pageNo>=1`，`pageSize<=200`）。
3. 解析时间范围和 `sourceType`。
4. 先 count，再 page 查询 `knowledgeBaseService`。
5. 封装 `PagedResponse` 返回。

### `POST /luna/api/query/log`（含 `/page`）
1. 空 body 时创建默认查询对象。
2. 构造 `LambdaQueryWrapper`：按 logType/module/action/content/traceId/operatorId/time 条件动态拼装。
3. 按 `createAt desc` 分页查询。
4. `logType` 枚举非法会抛 `IllegalArgumentException`，返回 `400`。

### `POST /luna/api/query/memory`（含 `/page`）
1. 接口已退役。
2. 固定返回 `410` 与迁移提示。

### `POST /luna/api/query/user-preference`（含 `/page`）
1. 接口已退役。
2. 固定返回 `410` 与迁移提示。

## 5.8 Prompt 治理（逐接口）

### `GET /api/prompt/categories`
1. `PromptQueryService.listCategories` 调 registry 列举分类。
2. 优先读取 `prompt_category` 启用分类，失败时回退到 item 推导。

### `GET /api/prompt/categories/detail`
1. 读取启用分类并按排序返回。
2. Controller 补充 `keywordMatchAllowed/executionCategory/enabled` 视图字段。

### `GET /api/prompt/categories/tree`
1. 读取启用分类。
2. 按 `parentCategoryKey` 组装树结构。

### `GET /api/prompt/items`
1. 构造分类查询请求（默认 `enabled=true,pageSize=500`）。
2. `PromptQueryService.search` 过滤后返回条目。
3. `PromptFrontendAdapter` 转换为 key-value 视图。

### `GET /api/prompt/item/detail`
1. 按 key 查 prompt（包含 disabled）。
2. 命中返回完整 record，未命中返回空对象。

### `GET /api/prompt/item/detail-by-id`
1. 按 id 查 prompt（包含 disabled）。
2. 未命中返回空对象。

### `GET /api/prompt/item/exists`
1. `PromptRegistryService.existsByKey` 检查是否存在（含 alias 命中）。
2. 返回 `{key, exists}`。

### `GET /api/prompt/item/key-values`
1. 按 category 拉取活跃 prompt。
2. 返回 key->value map。

### `POST /api/prompt/search`
1. 标准化搜索条件（分页、分类、模糊匹配、启用状态等）。
2. 从 registry 全量过滤后分页切片返回。

### `POST /api/prompt/item/create`
1. 校验 key 规范、分类存在性、分类前缀一致性。
2. 限制仅允许 content category 创建，禁止模板变量和 `${...}` 占位符。
3. 插入 `prompt_item`，再插入 active 版本。
4. 回写 `current_version_id`。

### `POST /api/prompt/item/update`
1. 按 key 加载 item/currentVersion。
2. 校验 editPolicy、runtime_slot、分类迁移合法性、assembly mode 合法性。
3. 区分执行类与内容类 prompt 的约束（执行类不能被禁用）。
4. 更新 item 主记录，新增版本记录；非 preview 时激活新版本。

### `POST /api/prompt/item/save`
1. key 必填。
2. 若 key 已存在走 `update`，否则走 `create`。

### `POST /api/prompt/item/delete`
1. 按 key 查 item。
2. 执行类 prompt 或无 delete 权限会拒绝删除。
3. 允许时做软删除：`enabled=false,status=disabled`。

### `GET /api/prompt/item/versions`
1. 按 key 找 item。
2. 返回该 item 全部版本，按创建时间倒序。

### `GET /api/prompt/item/version/detail`
1. 按 `versionId` 直查版本。
2. 未命中返回空对象。

### `POST /api/prompt/item/activate`
1. 校验版本存在。
2. 先把该 item 其它 active 版本归档。
3. 激活目标版本，并更新 item 的 `currentVersionId/enabled/status`。

### `POST /api/prompt/item/rollback`
1. 校验 key 与 versionId。
2. 确认版本属于该 key。
3. 复用 activate 逻辑切回旧版本。

### `POST /api/prompt/item/draft`
1. 校验 key。
2. 读取当前最新版本作为基线。
3. 创建 `status=draft,isActive=false` 新版本。

### `POST /api/prompt/item/archive`
1. 校验版本存在。
2. 若是执行类 prompt 的当前版本，拒绝归档。
3. 否则置 `archived,isActive=false`，必要时清空 item 当前版本并禁用 item。

### `POST /api/prompt/item/diff`
1. 校验左右版本 ID。
2. 要求两个版本属于同一 prompt item。
3. 按行比较 `promptValue`，输出 `+/-` diffLines。

### `POST /api/prompt/preview/match`
1. `PromptResolverService.resolve` 执行完整匹配链：policy include/exclude -> matcher -> 去重 -> 排序 -> runtime slot 映射。
2. 返回 `matchedItems/rejectedItems`。

### `POST /api/prompt/preview/assemble`
1. 先走与 previewMatch 相同的 resolve。
2. 按 slot 聚合文本并生成 section 预览。
3. 返回 `slotMapping/assembled/sectionMapping/sectionAssembled/filteredOutItems`。

### `GET /api/prompt/policy/list`
1. 查询 policy 主表，按更新时间倒序。
2. 返回策略包列表。

### `GET /api/prompt/policy/detail`
1. 按 `policyId` 查主表和 currentVersion。
2. 聚合 include/exclude 列表后返回详情视图。

### `POST /api/prompt/policy/save`
1. `policyId` 必填。
2. 主表不存在则新建，存在则更新元数据。
3. 生成新版本并先归档旧 active 版本。
4. 新版本设为 active，并回写主表 `currentVersionId`。

### `POST /api/prompt/policy/delete`
1. 按 policyId 查主表。
2. 做软删除：`enabled=false`，description 增加 `[deleted]` 标记。

### `GET /api/prompt/policy/versions`
1. 按 policyId 查主表。
2. 返回其全部版本。

### `POST /api/prompt/policy/activate`
1. 校验 policy 与目标版本归属关系。
2. 归档当前 active 版本。
3. 激活目标版本并更新主表 currentVersionId。

## 7. 核心链路组件职责映射
- `StateDrivenContextPipelineImpl`：统一 orchestrate/hydrate/execute/writeback 框架，负责把 round 请求补齐并调用 `RoundPipelineOrchestrator`。
- `TaskOrchestratorServiceImpl`：输入重构、恢复判定、node workset、工具决策输入、summary、round state 落库、审计 trace。
- `AgentServiceImpl`：治理签名校验、工具/资源/prompt/workflow 决策执行、工具 trace 回写。
- `RetrievalServiceImpl`：query 处理、route 选择、pipeline 执行与检索元数据汇总。
- `PlanOrchestratorServiceImpl`：计划生命周期编排（create/run/finalize/report）与阶段执行调度。
- `ApprovalServiceImpl`：审批中断任务管理、审批后恢复到聊天主链。
- `PromptResolverServiceImpl`：Prompt 匹配/去重/排序/slot 映射，直接影响工具决策和主模型提示词。

---

## 8. 关键配置对链路的影响
- `auth.*`：登录鉴权、JWT 过期、签名密钥。
- `luna.mcp.execution.allow-legacy-mode`：是否允许 LEGACY 工具执行模式。
- `luna.mcp.execution.allow-spring-bean`：是否允许 `SPRING_BEAN` 实现类型执行。
- `luna.mcp.compat.skill-endpoint-enabled`：是否启用 `/mcp/skills/approval` 兼容入口。
- `prompt.governance.*`：Prompt 解析器版本、策略强制规则、内置 fallback。
- `luna.rag.*` 与检索路由配置：影响 route 选择、topK、重排与超时。

## 9. 结论（面向 Review 的使用方式）
- 这套接口不是“Controller 调 Service”的直线调用，而是“治理驱动 + 状态驱动 + 可恢复执行流”。
- Review 重点应放在三类分支：
  1. 治理阻断分支（`503/422/pending`）是否符合预期。
  2. 审批/恢复分支是否能正确续接上下文。
  3. round state 与审计是否覆盖关键转移点（tool trace、snapshot、memory gate）。
- 排障时建议先定位入口接口，再沿本文件步骤对照 `state/audit/session` 三类落点检查。
